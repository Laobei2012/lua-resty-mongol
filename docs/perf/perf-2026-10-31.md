# Driver performance report: 2026-10-31

**Result:** The new driver meets the MongoDB 4.4 rps gate on all 11 comparable APIs in every valid run.
`insert_100` is the only API that misses a gate. It misses the p99 gate in two of three full runs ([#103](https://github.com/Laobei2012/lua-resty-mongol/issues/103)).

**Limits:** This report describes one shared cluster with fixed CPU limits.
It does not predict production throughput.

The measurements cover 2026-10-31 07:00 UTC through 14:34 UTC.
All 639 HTTP samples have zero non-2xx responses and zero socket errors.

The old driver cannot complete `find_100`, so that API has no ratio. The new driver reads 1,212 to 1,440 rps at 19.7 to 22.0 ms p99.

Read these results with the following limits:

- `insert_100`: The rps is about equal, and the new driver uses less CPU per request. But the slowest requests take longer in two runs. The cause is not known.
- `auth`: The gain includes the salted-password cache in the new driver. The two drivers do not do the same work, so this ratio is not a fair driver comparison.
- `auth` in run 2: The old-driver pass is invalid because wrk was throttled in 2 of 120 periods (1.67%). The old driver is slow on this API, so wrk ran in few periods. The rule treats this as invalid, and this report keeps that result.
- `gridfs_read`: The rps stays near 235 on both drivers and on every server version, although the new driver uses less CPU. A limit outside the driver likely sets this rate. The limit was not identified.
- `connect_nopool`: This API runs at four connections. Do not compare it with the 2026-10-29 report. Its rate varies widely between samples, and the cause is not known.
- Writes: With `safe` set, the old driver sends a legacy write and a separate `getlasterror` command. The new driver sends one write command. So the write ratios include this protocol change.
- Trend outliers: `gridfs_read` reached 273 to 353 ms p99 in a few runs. `insert_100` reached 245 ms p99 on MongoDB 9.0.4 in run 3. Other runs of the same API and version do not show this. The cause is not known.

## Changes since the 2026-10-29 report

The [first report](perf-2026-10-29.md) showed four APIs that failed the gates and one unstable API. All five now meet the rps gate. For example, the `find_one` ratio moved from about 0.54 to about 1.35.

Two things changed between the reports, so the ratios alone do not separate the causes:

- The driver: PRs #97, #99 and #101 made integer encoding, integer decoding and big-endian helpers faster.
- The test setup: The nginx CPU limit went from 300m to 1000m, and the load went from `-t1 -c8` to `-t2 -c16`.

The new-driver CPU per request points to the driver changes. In the first report, the setup throttled nginx in 78 to 84% of periods. In this report, nginx had no throttled periods.

## CPU interpretation

All 351 CPU rows per full run are available. Mean use is about 0.44 cores for nginx, 0.67 for Mongo and 0.07 for wrk. Nginx and Mongo had no throttled periods. Wrk was throttled in 0.02 to 0.03% of periods.

If nginx, Mongo or wrk is throttled in 1% or more of its periods, the run is invalid. Nginx did not reach its one-core limit, so the rps ratio does not measure driver CPU cost alone. Rps also depends on Mongo and the network. Nginx CPU per request shows the work inside nginx, and it does not gate.

The Mongo, nginx and wrk containers have CPU requests below their limits. Other pods on a node can slow them, and the throttling check does not detect this. Alternating old and new runs reduces this effect.

## Public data and reproduction

The [data directory](perf-2026-10-31-data/) has the HTTP, BSON and CPU results and the public manifest. The joined `old.jsonl` and `new.jsonl` files repeat the samples in the numbered pass files, so do not count both.

To recompute the tables, run `resty` from the repository root:

```bash
data=docs/perf/perf-2026-10-31-data/run-1
resty bench/compare.lua --cpu-file "$data/cpu.jsonl" \
  "$data/old.jsonl" "$data/new.jsonl"
```

Repeat with `run-2` and `run-3`. This command applies the CPU validity check and prints nginx CPU per request. Exit 1 is expected for runs 1 and 3, because `insert_100` misses the p99 gate. Exit 0 is expected for run 2, where `auth` is invalid.

## Setup

Three complete all invocations; each API uses the median of three measured samples. Only valid Mongo 4.4 A/B APIs gate: rps ratio >= 0.90 and p99 ratio <= 1.20. Invalid APIs count as neither pass nor fail. Trends do not gate.

Cluster context, node identities and node types are private. CPU request/limit and memory: Mongo 1000m/2000m and 4Gi, nginx 900m/1000m and 512Mi, wrk 200m/300m and 512Mi, clone 200m/200m and 128Mi. Mongo, nginx and wrk have CPU requests below limits and are Burstable; clone has equal requests and limits by owner decision (2026-10-30). Mongo cache is 1.5GiB; data emptyDir is 10Gi and ephemeral storage limit 12Gi.

Old `3eb6349db4d30b11aab271fb14a82b8504f6aa8e`; new `6cf0584ffe3e16008b73d695107e5430820f3159`; controller `6cf0584ffe3e16008b73d695107e5430820f3159`. OpenResty 1.31.1.1; wrk 4.1.0. Full source blobs and workload parameters are in [manifest.json](perf-2026-10-31-data/manifest.json).

Two threads, 16 connections (connect_nopool: 4), 10s socket timeout, 10s warm-up and 30s samples. BSON: at most 1,000 warm-up operations, stopping at 1s (checked every 50 operations); measure in batches of 100 operations until the first batch ends at or after 2s per case. Authentication is enabled; a gain on /auth includes the new driver's cached salted password optimization.
