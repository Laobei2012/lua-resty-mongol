# Driver performance report — 2026-10-29

The new driver misses the MongoDB 4.4 performance gates for `find_and_modify`,
`find_one`, `gridfs_read` and `ping` in all three complete invocations. `count`
is unstable: fail, pass, fail. Six other comparable APIs pass all three;
`find_100` is `n/a (old)` because the old cursor drops batches after the first.
These are valid completed measurements with threshold failures, not failed
benchmark executions.

The measurements cover 2026-10-29 17:17:53 UTC through 2026-10-30 08:44:26 UTC.
They describe this CPU-constrained shared-cluster setup. They do not establish
unconstrained production throughput or a driver-level cause for the regressions.

## Findings

| API | New/old median rps ratios, repetitions 1 / 2 / 3 | Gate outcome |
| --- | --- | --- |
| `find_and_modify` | 0.689 / 0.716 / 0.696 | Fail all three: throughput |
| `find_one` | 0.535 / 0.541 / 0.547 | Fail all three: throughput; also p99 in repetition 2 |
| `gridfs_read` | 0.780 / 0.796 / 0.793 | Fail all three: throughput |
| `ping` | 0.829 / 0.840 / 0.859 | Fail all three: throughput |
| `count` | 0.864 / 0.913 / 0.887 | Fail / pass / fail; also p99 fails in repetition 3 |

Each failed or unstable API has a `needs-triage` issue:
[`find_and_modify` #91](https://github.com/Laobei2012/lua-resty-mongol/issues/91),
[`find_one` #92](https://github.com/Laobei2012/lua-resty-mongol/issues/92),
[`gridfs_read` #93](https://github.com/Laobei2012/lua-resty-mongol/issues/93),
[`ping` #94](https://github.com/Laobei2012/lua-resty-mongol/issues/94), and
[`count` #90](https://github.com/Laobei2012/lua-resty-mongol/issues/90).

`auth`, `connect_nopool`, `delete_insert`, `insert_1`, `insert_100` and `update`
pass all three. The approximately 134–137× `auth` throughput gain includes the
new driver's known [salted-password cache](https://github.com/Laobei2012/lua-resty-mongol/blob/f5db50700458d2849dc11447383119c1cdc424a1/lib/resty/mongol/scram.lua#L165).
The benchmark does not isolate that optimization from every other driver change.
No profiling evidence identifies the causes of the slower APIs.

The BSON results show lower new-driver small-document encode/decode rates in
all three invocations, higher large-document decode rates, and mixed
large-document encode results. BSON has no pass/fail gate. These measurements
also run in the nginx container under its 300m CPU limit, with all 100,000
warm-up operations and two-second measurements retained for every case.

The first invocation's MongoDB 9.0.4 trend is slower on many APIs than the next
two: for example, `find_100` is 11.99 rps / 1044.657 ms p99, compared with
32.09 / 318.938 and 32.46 / 319.489. All three trend tables are retained.
Cross-version trends are informational and do not gate; this variability does
not establish a MongoDB-version or driver cause.

## Setup and coverage

Three sequential complete `all` invocations used the same cluster context,
same two nodes in the same region, sources, workload, resource profile and tools.
Mongo and the benchmark ran on separate nodes. The owner required cluster
context, node identities and node types to remain private; addresses, placement,
namespace ownership records, operational manifests, raw logs and host-local
paths are also withheld.

There are 639 unique HTTP samples and 24 BSON case results, with zero non-2xx
responses and zero socket errors. Each invocation has 33 old-driver samples,
36 new-driver samples and 144 new-driver trend samples, six interleaved A/B
pass files and all eight BSON cases. Namespace absence was independently
verified at 2026-10-30 09:00 UTC after the final cleanup.

An earlier interrupted foreground attempt with 99 HTTP samples is excluded
because it was incomplete, not because of its gate outcomes. The initial A/B
validation is also separate from these three complete invocations.

For MongoDB 4.4, the pass order is old/new repeated three times. Each API uses
one wrk thread, eight connections, a ten-second socket timeout, a ten-second
warm-up and three thirty-second measured samples. Throughput and p99 use their
respective medians of the three samples. An API passes only if the new/old rps
ratio is at least 0.90 and the new/old p99 ratio is at most 1.20. Gates use the
raw, unrounded medians; displayed values and ratios are rounded only for reading.

Authentication is enabled. Pooled handlers authenticate new connections before
reuse; `auth` measures explicit SCRAM-SHA-1 authentication on a pooled socket.
Collections are re-seeded between APIs. The workload and fixtures are documented
in the [harness plan](../superpowers/plans/2026-10-27-performance-test.md#apis-under-test)
and [harness instructions](../../bench/README.md).

## CPU interpretation

All 351 exported CPU rows per invocation are available: 117 intervals for each
of nginx, wrk and Mongo. Across invocations, nginx is throttled in
77.59–83.51% of sampled cgroup periods, Mongo in 21.08–23.86%, and wrk in 0%.
Approximate mean usage is 0.271–0.273 cores for nginx, 0.021–0.022 for wrk and
0.208–0.223 for Mongo. The substantial throttling constrains interpretation
despite the fixed placement and interleaved A/B order.

These are aggregate cgroup deltas over HTTP warm-up, measured samples and
sequential snapshot overhead, not isolated per-request CPU costs or a separate
BSON CPU profile. CPU caps and other shared-cluster activity can affect the
measurements. Neither the observed throughput differences nor these counters
alone identify a driver cause or predict performance without these limits.

## Public data and reproduction

The [dated data directory](perf-2026-10-29-data/) contains exact copies of the
generated allowlisted HTTP/BSON JSONL, numeric CPU deltas and public manifest.
Joined `old.jsonl` and `new.jsonl` repeat the same samples held in the numbered
A/B pass files; do not count both copies as additional observations. No private
completion markers, run manifests, placement, operational logs or launch
metadata are included.

From the repository root, use OpenResty's `resty` with the committed
[comparator](https://github.com/Laobei2012/lua-resty-mongol/blob/f90e59412ebfdf6312676d20158675778844c4d3/bench/compare.lua):

```bash
data=docs/perf/perf-2026-10-29-data/run-1
resty bench/compare.lua "$data/old.jsonl" "$data/new.jsonl"
# Exit 1 is expected for the measured A/B threshold failures; invalid input is 2.
resty bench/compare.lua --trend "$data/new.jsonl" \
  "$data/new-6.0.jsonl" "$data/new-7.0.jsonl" \
  "$data/new-8.0.jsonl" "$data/new-9.0.jsonl"
```

Repeat with `run-2` and `run-3` to reproduce their tables. The public exports
support comparator reproduction; `report.py report` requires the original
private invocation trees, including completion/provenance and placement files,
so these public directories are not inputs to that full validator.
